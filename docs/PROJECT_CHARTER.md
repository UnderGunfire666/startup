# startup 项目总纲

> 本文是 `startup` 后续设计、实现与验收的基线。它描述当前仓库中已经存在的能力和明确的架构边界；“未来方向”不是已完成承诺，实施前仍应形成独立功能计划与契约测试。

## 1. 项目定位与体验目标

`startup` 是一款城市小店模拟经营原型。玩家不直接从菜单中挑选数值最优的店铺，而是先观察城市空间、调查区块和门面，再将选址、商品、人员、时间安排及经营结果串成可理解的决策链。

核心循环为：

`区域调查 → 门面发现/尽调 → 选址签约 → 店铺配置与布局 → 排班采购经营 → 日终结算 → 品牌扩张`

长期体验目标是让地图提供现实直觉，调查提供可靠情报，经营结果验证玩家判断。项目不以交通、建筑或角色动作模拟为目标。

## 2. 当前架构

### 运行结构

- `scenes/Main.tscn` 是游戏入口，承载主界面、地图、经营面板与布局编辑器入口。
- `GameManager` 是领域编排层：加载静态数据、管理玩家与店铺、推进开店流程、驱动采购/经营结算，并向 UI 发出状态通知。
- `SaveManager` 读写 `user://savegame.json`；`TimeManager` 推进游戏时钟和营业时段；`ScheduleManager` 安排并结算玩家行动；`EventManager` 管理定义、活动事件与临时修正。
- `data/*.json` 是静态世界与商品目录；`scripts/resources/**` 将其转为强类型领域对象；`Store` 和 `PlayerState` 是主要运行时与存档状态。
- UI 只调用领域 API 或订阅信号；空间计算、结算、校验和布局投影保持在独立脚本中，避免界面节点成为规则来源。

```text
JSON 静态数据 → GameData → GameManager / 领域对象
                         ↓
PlayerState + Store + 时间/行动/事件状态 → SaveManager
                         ↓
主场景与各面板 ← 信号、查询结果与契约化计算
```

### 数据与兼容原则

- 静态道路、区块、门面、玩家住宅、商品和员工目录不写入存档；存档只保存玩家、店铺、时间、排班和事件等动态状态。
- 新字段必须为旧存档提供缺省行为。布局版本通过 `Store.layout_grid_version` 迁移；旧的家具和门面位置在首次使用布局时映射至当前网格。
- 世界数据的引用完整性由 `MapDataValidator`、道路图和地图编辑器契约测试共同保护。

## 3. 模块总览

### 3.1 玩家、角色与开店阶段

**目的**：保存玩家资源、特质、技能、精力、压力、位置及市场认知，并约束从建角到正式营业的流程。

**已实现**：角色创建、难度/特质、现金与精力压力、工作技能、区块位置、区域情报、区块理解度、门面尽调进度和玩家当前监管店铺。`Store.PreOpenStage` 划分建角、区域调研、门面选择、店铺筹备和开业阶段。

**实现原理**：`PlayerState` 承担跨店的玩家进度；`Store` 承担单店状态。`GameManager` 检查阶段前置条件并将结算结果分别应用到玩家和店铺。

**当前边界**：玩家移动只在城市网格上显示抽象标记和路线，不提供角色骨骼动画、开放世界操控、成长树或复杂人生事件。

**未来方向**：扩充特质与技能对调查、服务和经营决策的差异化；将玩家注意力和多店监管成本纳入玩法。

### 3.2 城市地图、道路与区域

**目的**：以真实空间关系支撑调查、移动、选址与门面价值判断。

**已实现**：运行时示例城区 `CR001` 含 83 个道路节点、83 条道路段、12 个区块、25 个门面和 3 处玩家住宅；`CR002`、`CR003` 作为后续区域保留。12 个区块均固化显式内部道路，住宅和门面通过保存的入口接入完整外部道路面。`CityMapCanvas` 绘制静态道路、区块、住宅、门面、入口、标签和选中轮廓；鼠标穿透的 `CityMapTravelLayer` 独立逐帧绘制路线与玩家位置。门面入口按已保存的立面布局精确映射并以青蓝色粗边显示。

**实现原理**：`RoadGraph` 提供抽象道路关系；`MapNavigationGrid` 以完整外部道路面、显式内部道路和地点入口计算正交最短路径，实例由 `GameManager` 缓存并在地图数据或门面入口变化时显式失效。住宅本体只通过保存的入口双向接入，不会成为穿越区块的捷径。静态地图缓存门面入口和标签布局，移动层缓存路线坐标及累计长度。道路仍是结构与旅行网格，而非实时车辆系统。

**当前边界**：地图没有实时交通、拥堵、行人、车辆、开放世界寻路或动态建筑渲染。

**未来方向**：新增更多城区及数据包、地图缩放/筛选体验、可视化地标与区域事件；保持道路图只服务空间关系和抽象移动。

### 3.3 调查、门面发现、尽调与选址

**目的**：让玩家从不完全信息逐步得到可用于选址的情报。

**已实现**：区块调查、连续区域研究、调查范围覆盖、门面初步查看和完整尽调、门面选择与签约。调研期间会在区块内部道路及直接相邻的外部道路上显示可重现的随机步行和停顿，但不改变权威结算位置。旅行抵达门面即记录到访：任何到访解锁只读门头，营业中抵达永久解锁只读店内平面与 3D。地图详情同时显示门面名、实际店名、营业时段、当前营业状态和可靠的开/关门倒计时。

**实现原理**：`ScheduleManager` 将调查作为消耗游戏时间的行动；`SurveyAreaCalculator` 计算覆盖权重；`GameManager` 保存调查与尽调状态，并通过信号刷新地图和面板。

**当前边界**：调查结果以当前固定数据和进度规则为主，没有完整的情报不确定性、竞争门店模拟或动态租约谈判。

**未来方向**：分层商业报告、门面缺陷/租约条款、竞品动态、调查事件和基于历史经营数据的再评估。

### 3.4 地图制作与数据校验工具

**目的**：以道路优先的工作流制作和验证静态城市数据，而不是依赖运行时节点树手工维护地图。

**已实现**：`MapAuthoringDocument`、`MapAuthoringCanvas` 与 `MapAuthoringPanel` 支持道路节点/路段、区块、显式内部道路、门面和住宅的创建、选择、修改、删除、导入导出、道路格重建及校验。属性侧栏只显示当前选中对象的设置；空间数据以 `roads.json`、`blocks.json`、`storefronts.json`、`player_homes.json` 四份文件往返。`MapDataValidator` 检查内部道路非空及连通、地点入口、占格冲突、区域归属和引用完整性。

**实现原理**：编辑器文档与运行时 JSON 模型共享领域数据结构，通过显式序列化连接，不让游戏规则依赖编辑器 UI。

**当前边界**：这是内部工具，尚非面向玩家发布的地图创作器；没有版本化内容包或协同编辑。

**未来方向**：地图模板、批量校验报告、可视化数据修复和用户地图的独立 `user://` 导入流程。

### 3.5 店铺、品类、设备与商品目录

**目的**：表示一家具体店铺的选址、营业状态、经营目录和资产。

**已实现**：多店容器与当前活跃店铺、品类槽、商品价格覆盖、设备购买、库存容量、营业时段、开店准备度和开业状态。静态目录包括品类、商品、原料、设备和员工候选人。

**实现原理**：`Store` 保存一家店的动态数据；目录对象为静态定义。`GameManager` 按品类、设备、人员和存货检查开业条件并提供 UI 使用的查询 API。

**当前边界**：设备面积与经营能力已有基础计算，但布局位置尚未影响效率；没有供应商关系、合同或设备折旧。

**未来方向**：品类协同、设备升级/维护、供应商选择、店铺品牌共享规则和更完整的多店经营界面。

### 3.6 采购、库存与损耗

**目的**：让原料成本、库存可用量和浪费进入日常经营决策。

**已实现**：采购购物车与总价计算、原料库存、加权平均成本、按配方预留和消耗、准备损耗、保质损耗及采购历史。结算记录收入、原料成本、租金、人工、水电、损耗和利润。

**实现原理**：每个 `Store` 保存原料库存与均价；订单先验证完整配方再扣减，避免半扣库存。`SettlementEngine` 和 `CustomerSimulator` 汇总成本及未满足订单原因。

**当前边界**：价格为静态或基础修正，没有供应链波动、仓储物流和多仓调拨。

**未来方向**：供应商报价、最低订货量、季节性、配送周期、动态价格和跨店库存调度。

### 3.7 员工、排班与玩家行动

**目的**：把可用人力和玩家时间转化为营业能力与调查进度。

**已实现**：员工雇佣、技能、小时段排班、玩家监管、每日行动表、立即行动、连续区域调查、深度勘验、行动中断和网格道路驱动的跨区移动。玩家从住宅专用格出发；可步行、骑行、乘公共交通或开车，按方式结算时间、精力与费用。停止移动时，若处于两格之间会补足到路径上的下一格，并按实际执行时长结算，绝不瞬移到最终目的地。

**实现原理**：`DaySchedule`、`ScheduledActionEntry` 和 `CurrentActionState` 表示日程；`ScheduleManager` 在小时推进时检查条件、累计持续行动并通知领域服务。员工技能覆盖影响服务与经营计算。

**当前边界**：没有员工 AI、班表偏好、离职、培训、工资谈判、停车/拥堵、公共交通班次或真实交通 Agent。

**未来方向**：排班优化、员工状态和成长、店长委派、远程监管与多店时间冲突。

### 3.8 时间、客流与经营结算

**已扩充：范围化线下竞争。** 同品类门店在任一方 `competition_radius` 覆盖另一方时进入竞争集合。每个区块/人群/品类/时段只生成一份有限自然需求，并按距离修正后的门店 `offline_influence`、菜单商品 `offline_influence` 与既有可达性、口碑、线下知名度分配。由此，强店获得更多销量时会同步减少同池门店可获得的自然客流。该规则不作用于知名度、口碑本身，也不作用于营销/广告引来的线上目的性客流；线上竞争力暂未实现。

**目的**：按游戏时间把选址、价格、库存、人员和营业状态转化为可解释的经营结果。

**已实现**：可暂停/倍速的游戏时钟、小时推进、营业时段、顾客到达与排队、到店转化、产能/库存/等待时间导致的损失、时段结算和日终汇总。自然客流、道路可达性、门面截获、目的性客流、声誉及区块知名度已有基础实现。

**实现原理**：`TimeManager` 驱动时段；`CustomerSimulator` 以到达、服务与队列状态模拟单时段订单；`SettlementEngine` 产出 `SettlementResult`，再由 `Store` 和 `PlayerState` 应用。空间客流使用 `TradeAreaCalculator`、`PopulationSupplyCalculator` 和道路距离计算。

**当前边界**：经营模型仍是原型数值模型，布局、装修、季节和复杂竞品尚未进入结算；不模拟每个真实顾客的地图路径。

**未来方向**：需求波动、竞争店、营销、消费群画像细化、布局效率和长期财务系统。

### 3.9 知名度、事件与临时修正

**目的**：使店铺经营结果和城市环境产生短期扰动与长期品牌扩散。

**已实现**：按区块保存的店铺知名度、道路曝光与门面影响范围、口碑带来的基础传播、目的性客流来源计算。事件框架包含事件定义、活动事件、通知/决策/中断、作用域和临时修正，并可影响玩家、区块、区域、门面或店铺。

**实现原理**：`EventManager` 保存事件生命周期；`EventEffectResolver` 将效果提交到对应领域；`TemporaryModifier` 避免直接污染静态道路和区块数据。详细设计参见 [事件系统规划](event_system_plan.md)。

**当前边界**：事件内容量和长期品牌玩法仍有限；线上传播、营销活动和多店品牌协同未完整实现。

**未来方向**：扩充事件库、冷却与权重、营销渠道、线上知名度、区域活动及品牌网络效应。

### 3.10 室内与门面布局（2D / 正交 3D）

**目的**：让玩家能以一致的真实尺度布置店内设备和临街门面，并为未来视觉和经营规则提供稳定数据基础。

**已实现**：店铺编辑器提供“室内”“室内 3D”“门面”“门面 3D”视图。室内支持设备选择、点击放置/移动、旋转、删除和有效/无效拖放预览；门面支持招牌、入口、橱窗的放置、选择、拖放和删除。室内 3D 使用固定 45° 正交俯视，门面 3D 使用正交立面视图；两者均与对应 2D 视图共享布局数据。

布局已接入首版经营规则：经营所需设备必须摆放才会生效；入口必须存在且门内两格保持净空；招牌提升进店截获，橱窗提升线下知名度增长。未摆放设备仍是已购资产，但不提供营业能力、储存效果或设备电费。

**实现原理**：

- `StoreFurniturePlacement` 保存 `instance_id`、设备 ID、格坐标和 90° 步进旋转；`StoreFacadePlacement` 保存组件类型和格坐标。
- `InteriorLayoutValidator` 与 `FacadeLayoutValidator` 在提交前统一检查边界、可用格、重叠和组件数量。无效拖放不改写数据。
- `StorefrontLayoutGeometry` 将每个 3.5m × 3.5m 的城市格精确细分为 7 × 7 个布局格；每格 `0.25㎡`，在 3D 中对应 `0.5m`。它从门面的实际占用格导出室内可用掩码、临街边界和门头宽度，因此 L 形、转角和多格门面不再被面积估算成错误矩形。
- `FacadeProjection3D` 和 `InteriorProjection3D` 共享格坐标到世界坐标及反算规则。门面入口的横向位置映射到室内前墙；室内 3D 只在布局中实际存在入口时绘制开口。
- 每个门面数据具有临街边方向和默认入口偏移。首次初始化布局时生成可编辑的预设入口；删除后通过 `facade_layout_initialized` 记录，不会自动重新生成。

**当前边界**：2D 已使用图集 Sprite、3D 仍以程序化低模为主；布局不计算复杂邻接协同、厨房动线或员工寻路。墙体、门口和素材仍不可编辑。

**未来方向**：替换 Sprite/模型和材质、增加真实不规则墙体轮廓与门窗表现、将合理的设备/门头指标接入经营模型。保持墙体编辑、物理碰撞、员工寻路和 3D 资产制作作为独立阶段，避免和当前布局数据层耦合。

### 3.11 存档与版本迁移

**目的**：保存完整动态游戏状态，并允许系统演进时继续加载旧存档。

**已实现**：玩家、店铺、库存、员工、排班、时间、事件、家具布局和门面布局均支持往返存档。未含门面/家具布局的旧存档加载为空布局；旧布局网格在首次打开编辑器时映射到当前 0.25㎡ 网格。无效旧 UID 与旧 `RegionData` 解析问题已清理。

**实现原理**：各领域对象提供 `to_save_dict()` / `from_save_dict()`；`SaveManager` 只处理序列化入口，兼容规则留在领域对象和布局面板中。

**当前边界**：存档为单文件、本地手动保存，未做云同步、多个存档栏位或迁移可视化报告。

**未来方向**：版本化迁移日志、多个存档槽、自动备份、导入导出和异常存档恢复。

### 3.12 UI、报告与测试

**目的**：提供可操作的经营界面，并用低成本自动检查保护领域规则。

**已实现**：角色创建、行动、品类、采购、员工、排班、门面、营业、历史、报告、存读档、店铺列表和地图面板。地图将静态内容与逐帧移动分层，普通 UI 时钟刷新最多 10Hz；导航、路线、入口和标签布局使用事件驱动缓存，经营动态使用最多 20 条的固定 Label 池，并只接收当前玩家店铺事件。测试以独立 Godot 场景的契约测试为主，覆盖核心状态、选址、道路图、地图编辑、调查、旅行停止、门面访问、存档、员工、实时经营、事件、室内布局、门面布局和室内 3D。

**实现原理**：UI 通过 `GameManager`/Autoload 查询和信号刷新，不复制领域规则；每项高风险计算或迁移用 `tests/*ContractTest.tscn` 固化输入与期望。

**当前边界**：主场景的交互体验仍需要持续人工检查；30 秒等价契约与 Windows 真实渲染验收已经保护静态/动态图层、路线与导航缓存、节点数量、真实分段帧时和倍速权威结果，但仍没有完整 UI 自动化、跨硬件性能矩阵或发布流水线。

**未来方向**：UI 状态测试扩展、截图回归、性能分析、可访问性、教程与错误提示统一。

## 4. 已确认的空间与布局规范

| 主题 | 规范 |
| --- | --- |
| 运行时示例地图 | `CR001`；道路、区块、门面和住宅分别由 `data/roads.json`、`data/blocks.json`、`data/storefronts.json`、`data/player_homes.json` 提供。 |
| 区块内部道路 | `internal_road_cells` 是区块内唯一普通可走面；空列表属于数据错误，不回退为整块可走。 |
| 地点入口 | 门面和住宅占格不与道路重叠；地点格仅通过保存的正交相邻入口接入导航网。 |
| 城市地图格 | 3.5m × 3.5m，即 12.25㎡。 |
| 布局格 | 每个城市格细分 7 × 7；单格 0.25㎡。 |
| 3D 世界尺度 | 一个布局格等于 0.5m。 |
| 门头与室内 | 门头宽度来自临街边界；室内可用格来自门面真实占用轮廓，而非面积估算矩形。 |
| 入口 | 初始入口来自门面预设；玩家可移动或删除。只有实际 `facade_layout` 中的入口会在室内 3D 形成开口。 |
| 视图一致性 | 2D 和正交 3D 是同一布局数据的两种编辑表现，不新增独立 3D 存档格式。 |

## 5. 架构边界与开发准则

1. 静态世界数据和动态游戏状态必须分离；事件等短期变化应使用运行时状态或修正器，不能直接改写道路、区块和门面的定义数据。
2. UI、地图画布和 3D 画布不得成为业务规则来源；选择、放置、结算和迁移必须经过领域服务或验证器。
3. 地图应支持现实直觉和抽象距离，不发展为实时交通、开放世界或逐个角色寻路模拟。
4. `Awareness` 与 `Reputation` 保持分离：前者表示哪些区块知道店铺，后者表示评价；两者不应合并成一个倍率。
5. 布局数据先保证尺度、占格和保存稳定，再引入美术表现、墙体编辑或经营效果。任何布局效率机制必须有独立的可解释公式和回归测试。
6. 每次扩展存档结构都必须提供旧存档缺省行为或迁移路径，并新增往返测试。
7. 每次改动道路、区块、内部道路、门面、住宅数据或地图编辑器时，必须运行道路图、地图数据、移动旅行和地图编辑器契约测试，并显式失效导航缓存。
8. 动画层可以逐渲染帧更新，但不得借助高频时钟信号重建静态地图、导航网或普通 UI；性能优化不得丢弃、重排经营事件或改变权威结算。

## 6. 验证基线

开发修改应按影响范围运行相关 `tests/*ContractTest.tscn`。当前重点覆盖包括：

- 核心状态、存档往返、开店阶段与 UI 状态；
- 道路图、区域 ID、区块选择、显式内部道路、住宅、调查序列、地图编辑工作流、道路邻接、旅行停止、门面占用与门面显示；
- 员工/运营、实时结算与事件系统；
- 室内布局、门面布局及室内 3D 投影与迁移。
- 30 秒等价地图移动性能、静态/动态绘制计数、路线与导航缓存、节点稳定性，以及 1/2/5 倍速权威结果一致性。

提交前至少执行 Godot 无头编辑器扫描，并在触及相应领域时运行对应契约场景。涉及主场景交互、地图命中或 SubViewport 3D 画布时，还应在本机编辑器手动验证可见性、点击、拖放、保存和重新进入后的状态。

## 7. 推荐开发路线

1. **完成空间数据往返收尾**：5 倍速 30 秒真实渲染验收已经通过；下一步固化地图编辑器四文件往返、住宅编辑、入口同步和旧存档迁移。执行细节见[短期开发计划](short_term_plan.md)。
2. **完善空间表达**：用美术资产替换布局占位表现，补齐不规则室内墙体轮廓和地图可读性，但不改变布局数据格式。
3. **布局进入经营**：在可解释且可测试的前提下，让设备配置、门头与入口影响容量、曝光、转化或服务效率。
4. **经营深度**：扩展供应链、员工管理、竞品、营销、区域事件和知名度传播。
5. **多店扩张**：完善跨店排班、监管、品牌协同、区域扩张和多店报告。

每一阶段应保持当前边界：先以领域规则、存档兼容和契约测试稳定数据模型，再扩展表现层与内容量。
