# 世界空间、客流与事件系统设计

## 1. 文档目的

本文用于固化大地图、道路、区块、门面、移动、客流、知名度与事件系统之间的设计边界和联动关系。

核心目标不是模拟完整城市，而是让玩家能够像现实经营者一样：

- 从地图外观形成对区块和门面的初步判断；
- 通过调查验证、修正这些判断；
- 在真实的空间距离和位置差异下做选址与经营决策；
- 让道路、门面、品牌和事件共同影响经营结果；
- 保持系统足够轻量，不发展成交通或城市模拟游戏。

长期核心体验：

`观察地图 → 形成商业判断 → 调查获取可靠信息 → 选址 → 开店 → 经营验证 → 品牌扩散 → 多店布局`

---

## 2. 大地图系统定位

大地图不是开放世界移动地图，也不是单纯的传送菜单，而是玩家进行经营判断和多店布局的主要空间界面。

地图需要尽量通过视觉和空间关系表达现实直觉，而不是把所有信息都隐藏在数值面板中。

### 2.1 玩家无需调查即可看出的信息

属于现实中肉眼可见的信息，例如：

- 学校、写字楼、住宅区、工业园、商业街等城市形态；
- 道路宽窄、道路类型和空间连接关系；
- 门面是否临街、位于路口、主路、支路或小巷；
- 门面与学校、地铁口、商业中心等明显地标的空间关系；
- 已发现门面的实际地图位置。

这些信息用于让玩家先凭生活经验形成假设。

### 2.2 调查系统提供的信息

调查的目的不是让地图“从黑盒变成表格”，而是验证和精化玩家的直觉。

调查后逐步获得：

- 客群结构；
- 活跃时间；
- 消费能力与价格敏感度；
- 品类需求；
- 竞争状况；
- 门面隐藏缺陷；
- 更精确的道路与位置商业价值判断。

原则：

> 地图负责让玩家产生判断，调查负责让玩家获得可靠情报，实际经营负责最终验证判断。

## 3. 道路系统：地图骨架，而非交通模拟

道路必须是有逻辑意义的地图对象，而不能只是视觉装饰。

道路承担三个职责：

1. 作为地图制作的空间骨架，避免区块和门面脱离城市结构；
2. 建立区块之间的空间连接关系；
3. 提供道路距离，用于计算玩家跨区移动耗时。

当前阶段明确不做：

- 实时车辆模拟；
- 拥堵；
- 红绿灯；
- 公交 / 地铁线路模拟；
- 每个行人的路径；
- 道路容量和实时交通流量。

这些系统会显著增加复杂度，并把游戏推向城市模拟方向。

### 3.1 推荐道路数据结构

道路逻辑采用轻量 Road Graph：

- `RoadNode`：道路端点、路口等连接节点；
- `RoadSegment`：连接两个 RoadNode 的道路段；
- RoadSegment 的几何长度用于路径长度计算。

道路图只需要支持最短道路距离计算，不需要支持实时交通 Agent。

### 3.2 地图制作约束

地图编辑流程应以道路为第一层：

`创建 Road Graph → 创建 Block → Block 关联道路入口 → 放置 Storefront → Storefront 关联道路`

建议规则：

- Block 至少有一个有效道路入口；
- Storefront 必须关联附近 RoadSegment；
- Validator 检查孤立道路、无入口 Block、脱离道路 Storefront 等错误；
- 不要求所有 Block 必须被道路完整围合，以兼容校园、工业园、大型住宅区等现实结构。

## 4. 玩家移动系统

移动系统的目的仅是避免跨区瞬移造成出戏，并让空间距离产生时间成本。

不把移动本身做成核心玩法。

### 4.1 移动模型

跨区移动耗时基于 Road Graph 的最短道路距离：

`当前 Block 道路入口 → Road Graph 最短路径 → 目标 Block 道路入口`

概念公式：

`travel_time = road_distance / abstract_move_speed`

`abstract_move_speed` 是数值调节参数，不代表具体交通方式模拟。

### 4.2 表现层

玩家点击目标区块后：

- 显示预计耗时；
- 时间正常推进；
- 地图可以播放轻量移动动画；
- 不需要真实路径跟随、NavigationAgent 或车辆系统。

后期多店经营时，空间距离可以进一步形成“玩家注意力成本”：远距离店铺发生重大事件时，玩家需要决定是否花时间赶过去。

## 5. Road Accessibility

### 5.1 定义

`Accessibility` 表示消费者到达该道路沿线门面的容易程度。

它不是道路容量，也不是车流量。

它回答的问题是：

> 一个已经在附近活动、并有潜在消费意愿的人，能否方便地到达这条路沿线的店铺？

### 5.2 典型道路语义

- 高速 / 快速路：Accessibility 很低，因为沿途难以随时进入门面；
- 城市主干道：Accessibility 高，连接性强且通常存在沿街入口；
- 商业街：Accessibility 很高；
- 社区道路：Accessibility 高，居民容易抵达；
- 步行街：Accessibility 很高；
- 小巷：Accessibility 中低，虽然可进入，但通常绕、难找或入口有限。

### 5.3 对经营的影响

Accessibility 主要参与本地自然客流形成过程。

它不创造人口，只影响附近潜在消费者能否顺利到达门面。

---

## 6. Road Exposure

### 6.1 定义

`Exposure` 表示道路沿线门面被路过或在附近活动的人注意到的概率与机会。

它不是交通流量的直接等价物。

高流量并不必然意味着高曝光：车速、道路形态、商业环境和停留时间都会影响有效商业曝光。

### 6.2 典型道路语义

- 高速 / 快速路：流量大但速度快，Exposure 一般；
- 城市主干道：人流车流大、速度相对适中，Exposure 很高；
- 商业街：消费者本身就在观察商业环境，Exposure 很高；
- 步行街：虽然无车流，但停留与观察时间长，Exposure 很高；
- 社区道路：经过人口相对固定且流量有限，Exposure 低；
- 小巷：总流量低，Exposure 很低。

### 6.3 Exposure 不直接增加当前 Visitors

这是重要边界。

Exposure 不应简单写成：

`Visitors × ExposureModifier`

否则只能体现“今天多来一点人”，无法表现品牌长期积累和跨区影响。

正确方向是：

`Road Exposure × 门面影响范围覆盖比例 → Block Awareness 增长`

因此：

- Accessibility 主要影响当前本地客流；
- Exposure 主要影响未来品牌知名度，不直接增加当前 Visitors。
- Exposure 只影响门面线下影响范围覆盖到的 Block；范围外 Block 不获得这部分知名度。

## 7. Storefront Capture

`Capture` 属于具体 Storefront，而不是道路。

它表示：

> 已经经过或到达这个位置的人，有多大概率被这个具体门面截获并形成实际访客。

同一条道路上的不同门面可以有完全不同的 Capture。

影响来源可包括：

- 是否位于路口；
- 门头可见性；
- 是否被建筑遮挡；
- 是否位于二层或内街；
- 门面宽度；
- 与人流方向的关系。

现有 `StorefrontData.capture_modifier` 可以继续承担这一层职责。

---

## 8. 自然客流模型

自然客流描述：

> 玩家并不是专程寻找这家店，而是本来就在附近活动，并因为位置、需求和门面条件产生到店行为。

概念链路：

`Block Population / PopulationSupply`

`→ 时段活动人口`

`→ 客群与品类需求`

`→ Trade Area`

`→ Road Accessibility`

`→ Storefront Capture`

`→ Natural Visitors`

其中：

- Population 决定“有没有人”；
- Block 决定“是什么人、什么时候出现、有什么需求”；
- Accessibility 决定“这些附近的人是否方便到达”；
- Capture 决定“到达或经过以后，这个具体门面能截获多少人”。

Road 不直接生成消费者。

---

## 9. Awareness：独立于自然客流漏斗的知名度系统

### 9.1 为什么必须独立

品牌知名度不能只是当前客流漏斗上的倍率。

如果只对当前 Trade Area 内 Visitors 加成，就无法表现现实中的：

- 知名店吸引远处消费者专程前往；
- 品牌影响范围逐渐扩大；
- 多家分店共同增强品牌覆盖；
- 小巷中的优质店铺通过口碑突破地理限制。

因此 Awareness 应形成独立的第二套客流来源。

### 9.2 Awareness 与 Reputation 必须分离

`Reputation`：知道这家店的人如何评价它。

`Awareness`：有多少人知道这家店，以及哪些区域的人知道它。

典型组合：

- 高 Reputation + 低 Awareness：社区宝藏店；
- 高 Reputation + 高 Awareness：城市名店；
- 低 Reputation + 高 Awareness：知名但评价不佳；
- 低 Reputation + 低 Awareness：普通新店或弱势店铺。

现有 `Store.reputation` 不应承担 Awareness 职责。

### 9.3 门面线下影响范围

每个 Storefront 具有独立的 `awareness_radius`（影响范围系数）。以门面地图位置为圆心、该半径为圆，圆覆盖到的 Block 才会获得该门面的线下知名度。

覆盖比例按网格结算：

`coverage_ratio = 被影响范围覆盖的 Block 网格数 / Block 总网格数`

- 完全位于圆内的 Block 获得完整效果；
- 一半网格位于圆内的 Block 获得 50% 效果；
- 完全在圆外的 Block 不获得线下曝光知名度；
- 该范围模拟路过、附近居民观察与线下口口相传，因此不应无限扩散到远区。

线下曝光的单时段知名度增长概念式为：

`road_exposure × storefront_exposure_modifier × awareness_radius_coverage × 经营状态修正`

道路等级、道路 Exposure 和门面自身属性只决定“被看见与被记住的机会”；它们不直接创造自然客流。

### 9.4 Awareness 应具有空间维度

长期推荐按 Block 保存，而不是一个 Store 全局数值：

`awareness_by_block[block_id] = value`

这样可以表现：

- 本店附近 Block 高知名度；
- 邻近区域逐渐扩散；
- 远区知名度较低；
- 营销、口碑和事件造成特定区域传播；
- 多店品牌影响范围重叠。

### 9.5 Awareness 的主要增长来源

- Road Exposure 在门面影响范围内带来的自然曝光；
- 实际顾客在门面影响范围内带来的线下口碑传播；
- 营销；
- 开业活动；
- 社交媒体 / 媒体事件（未来的线上知名度系统）；
- 特定随机事件；
- 多店品牌协同。

Exposure 只是线下 Awareness 的一个自然增长渠道，而不是唯一来源。线上知名度是后续独立系统：它可以突破门面影响范围，但本阶段仅保留概念，不设计数值或实现。

## 10. Destination Visitors：目的性客流

目的性客流描述：

> 顾客已经知道这家店，并且愿意为了这家店从其他 Block 专程前往。

它与自然客流独立计算。

概念链路：

`门面在其他 Block 的 Awareness`

`→ Reputation（高低都会加速传播）`

`→ 品类吸引力 / 当前消费需求`

`→ 距离衰减`

`→ Destination Visitors`

最终总访客：

`Total Visitors = Natural Visitors + Destination Visitors`

规则边界：

- 只计算门面所属 Block 以外的 Block，避免与 Natural Visitors 重复；
- Awareness 只表示“知道门面存在的人数比例”，不代表好评；
- 高口碑与低口碑都会让经历更容易被记住，因此都会加速 Awareness 传播；
- 高口碑提高目的性客流转化，低口碑降低目的性客流转化。

这样能够体现：

- 好位置帮助新店快速起量；
- 差位置但经营优秀的店可以依靠口碑成长；
- 高知名度店铺可以突破当前 Trade Area；
- 多店布局不只是增加销售点，也可能扩张品牌覆盖范围。

## 11. 两套客流机制的边界

### 11.1 空间 / 自然客流线

`Population → Demand → Trade Area → Accessibility → Capture → Natural Visitors`

主要回答：

> 附近本来就存在的人，会不会自然走进这家店？

### 11.2 品牌 / 目的性客流线

`线下 Exposure / 线下口碑 / 未来线上传播 / Marketing / Events → Block Awareness → Reputation + Distance → Destination Visitors`

主要回答：

> 不在门店自然覆盖范围内的人，会不会因为知道并认可这家店而专程前来？

两条线只在最终 Visitors 层汇合。

---

## 12. 调查系统：确定性进度 + 随机事件

### 12.1 核心决策

保留现有 `block_understanding` / 调查进度，不改成纯随机获取信息。

原因：

- 纯随机会导致玩家重复调查却长期得不到关键经营信息；
- 门面发现等核心节点不能依赖运气；
- 稳定进度提供保底收益；
- 随机事件负责惊喜、提前发现和额外情报。

### 12.2 固定进度里程碑

调查达到指定阈值时触发确定性结果，例如：

- 早期：发现区块门面；
- 中期：揭示较可靠的客群、需求、竞争、租金或时段信息；
- 高进度：提供接近完整的经营画像。

关键里程碑必须保证触发一次，不可因 RNG 错过。

现有门面发现逻辑应继续作为确定性进度奖励。

### 12.3 随机调查发现

随机调查事件不承担核心流程推进职责。

可用于：

- 额外增加 `block_understanding`；
- 提前揭示商业信息；
- 提前发现某个门面，但不能成为唯一发现方式；
- 获得竞争、客群、租金、客流、道路或时段局部情报；
- 触发少量玩家资源或临时效果。

随机事件可以受以下因素影响：

- Block 类型；
- tags；
- 时间；
- 玩家当前位置；
- 当前行动；
- 已有知识。

但事件是否触发本身不需要与调查进度强绑定。

更高 `block_understanding` 可以影响事件信息精度，而不是简单提高随机事件数量。

## 13. 事件系统定位

事件系统不是独立剧情系统，而是空间、行动、经营和多店系统上的动态扰动与信息获取层。

优先覆盖：

1. 调查随机发现（Research Discovery）；
2. 玩家所在区块随机事件（World / Block Event）；
3. 店铺营业事件（Store Operating Event）。

### 13.1 事件作用域

事件必须显式区分作用域：

- PLAYER：玩家资源、精力、压力、知识；
- BLOCK：单个区块的状态、情报或临时变化；
- CITY_REGION：城市区域层效果；
- STOREFRONT：门面相关事件；
- STORE：单家企划或已开业店铺事件，必须显式 `store_id`。

### 13.2 三种交互级别

- NOTICE：纯通知，不暂停时间；
- DECISION：需要玩家选择，可进入待处理事件；
- INTERRUPT：少量重大事件，可暂停时间。

多店经营后禁止所有事件都强制弹窗暂停。

### 13.3 Temporary Modifier

事件未来可以对以下系统施加有限时长修正：

- 自然客流；
- 转化；
- 采购价格；
- 服务效率；
- Reputation；
- Awareness 增长；
- Block 活跃度；
- Accessibility / Exposure 的临时有效值。

静态 Block / Road 数据本身不应被事件永久修改；动态变化应通过运行时状态或 modifier 叠加。

## 14. 系统联动示例

### 示例 A：主干道上的新店

1. Block 本身存在大量午间办公人口；
2. Road Accessibility 高；
3. Storefront Capture 较高；
4. 因此开业后 Natural Visitors 较高；
5. Road Exposure 很高；
6. 每天自然获得较快 Awareness 增长；
7. 若 Reputation 同时较高，周边 Block 开始形成 Destination Visitors。

结果：好位置既帮助短期起量，也帮助品牌早期传播。

### 示例 B：社区小巷中的优质店铺

1. Accessibility 尚可但 Exposure 较低；
2. 初期 Natural Visitors 主要来自附近居民；
3. 品牌自然曝光增长慢；
4. 但如果 Reputation 很高，实际顾客持续产生口碑传播；
5. 邻近 Block Awareness 逐渐提高；
6. 最终产生跨区 Destination Visitors。

结果：差曝光位置并非必败，而是成长路径更依赖产品和口碑。

### 示例 C：快速路旁的门面

1. 道路物理流量可能很大；
2. 但 Accessibility 低；
3. Exposure 仅一般；
4. 因此不能因为“车多”自动获得高客流；
5. 玩家调查后可能意识到这是一个看似繁忙、实际商业价值有限的位置。

结果：避免“最大道路 = 最佳门面”的错误直觉。

### 示例 D：区域事件影响品牌与经营

某商业中心举办大型活动：

- Block 活跃人口短期上升；
- Natural Visitors 增长；
- Road Exposure 的有效曝光机会增加；
- 附近店铺 Awareness 增长加快；
- 若活动带来大量满意顾客，还可进一步形成口碑传播。

同一个事件因此可以同时影响即时经营和长期品牌，而无需模拟每个行人。

## 15. 地图编辑器方向

地图制作工具应采用“道路骨架优先”的工作流。

第一阶段推荐内部开发工具，而不是直接制作面向玩家的完整编辑器。

### 15.1 MVP 制作流程

`Road Graph → Block → Storefront → Validator → 导出静态数据`

可先使用 Godot Tool Scene / EditorPlugin 进行编辑。

需要支持：

- 绘制 RoadNode / RoadSegment；
- 调整道路形状；
- 创建和调整 Block；
- 为 Block 指定道路入口；
- 拖放 Storefront；
- 自动关联附近 RoadSegment；
- 校验地图结构；
- 导出到运行时使用的数据格式。

### 15.2 长期玩家自建地图

如果未来开放地图编辑：

- 编辑器 UI 与运行时数据模型分离；
- 共用 MapDocument / Serializer / Validator；
- 玩家地图保存到 `user://`；
- 必须验证 ID、道路连通、Block 入口、Storefront 位置和引用完整性。

不要让运行时核心系统依赖编辑器节点树。

## 16. 推荐实现顺序

### 最近完成：网格旅行、门面访问与地图性能分层

- 新增静态住宅数据；预设角色使用固定住宅与初始载具，自定义角色在创建时选择住宅且默认无载具。住宅占格只通过保存的内部道路入口接入导航，不会成为区块穿行捷径。
- 玩家位置、住宅、当前地图锚点和拥有载具写入存档；旧存档按预设或默认住宅迁移，同时保留已有区块位置。
- 出行方式为步行、骑行、公共交通和开车，均按外部道路面、显式内部道路及地点入口组成的网格最短路线计算距离与耗时；骑行/开车要求拥有对应载具，公共交通和开车按距离扣费，所有方式按实际时长消耗精力。
- 地图侧栏会展示所选区块或门面的方式、距离、时间、精力和费用；玩家必须先单独前往，抵达后才能调查或到访。
- 移动可以手动停止；若玩家位于两格之间，行动会补足至路径上的下一格，再按补足后的时间、精力与费用结算，不会瞬移到目的地。调研期间以确定性随机序列显示内部道路和相邻外部道路上的步行与停顿。
- 抵达门面即记录到访；普通到访解锁只读门头，营业中抵达永久解锁只读店内布局。地图同时显示实际店名、营业时段、营业状态及可靠的开/关门倒计时。
- 静态地图和玩家动态图层已经分离；导航网、路线、入口和标签布局均缓存，普通 UI 时钟刷新最多 10Hz，隐藏经营面板不再持续创建/销毁顾客事件节点。
- Godot 无头脚本扫描、正式地图、地图编辑器、地图展示、旅行、事件和 UI 状态重点契约均已通过；30 秒等价与真实 Windows 渲染性能验收均已通过，下一步的空间数据往返收尾见[短期开发计划](short_term_plan.md)。

### 已完成基础

- 调查进度、门面发现、事件系统；
- Road Graph、地图制作工具、Block 入口、Storefront 道路关联与地图校验；
- 基于 Road Graph 的跨区移动耗时；
- 住宅作为开局位置、交通工具所有权、按道路距离结算的多方式出行，以及地图上的行程可视化；
- 自然客流、按 Block 保存的 `awareness_by_block`、口碑传播与目的性客流的第一版；
- 门面影响范围知名度：`Storefront.awareness_radius` 与曝光修正、圆形覆盖网格比例、仅向覆盖 Block 写入道路 Exposure 和线下口碑；

## 17. 架构边界

### 17.1 不把道路系统做成城市交通模拟

Road 只负责：

- 地图结构；
- 空间连接；
- 移动距离；
- Accessibility；
- Exposure。

不负责实时交通 Agent。

### 17.2 不让 Awareness 混入 Reputation

两者必须保持独立状态和不同玩法意义。

### 17.3 不让 EventManager 成为第二个 GameManager

推荐拆分：

- EventDefinition：静态事件定义；
- EventResolver：条件、权重、cooldown、抽取；
- ActiveEvent：运行时事件实例；
- EventEffectResolver：把结果提交给正确领域；
- UI：展示和选择。

Player effect 应作用于 PlayerState 或对应业务 API；Store effect 必须显式 `store_id`；时间仍归 TimeManager；行动上下文仍归 ScheduleManager。

### 17.4 动态世界状态与静态数据分离

道路、Block、Storefront 的基础结构属于静态世界数据。

施工、活动、临时封路、区域热度、曝光提升等动态变化应进入运行时状态或 Temporary Modifier，不直接污染静态定义。

## 18. 核心设计原则总结

1. 地图应让玩家先凭现实生活直觉判断，而不是先看数值表。
2. 道路是地图骨架，但不是交通模拟系统。
3. Population 决定有没有人，Block 决定是什么人和什么时候出现。
4. Accessibility 决定附近潜在消费者是否方便到达门面。
5. Exposure 决定门面获得自然品牌曝光的机会。
6. Capture 决定具体门面能截获多少经过和到达的人。
7. Natural Visitors 来自当前空间与需求条件。
8. Awareness 具有空间范围，并产生独立的 Destination Visitors。
9. Reputation 表示“知道以后觉得好不好”，不能替代 Awareness。
10. 好位置帮助快速起量，但长期高 Reputation 与 Awareness 可以突破地理限制。
11. 调查进度负责核心信息保底，随机事件负责额外、提前和动态信息。
12. 所有新增系统都应服务“投资 → 调研 → 选址 → 开店 → 经营 → 品牌扩张 → 多店投资”的主循环，而不是自成玩法孤岛。
